= Observing the Application

Running an application is part of the battle, but troubleshooting is the other.
The isolation that makes containers great, also means new tools to understand what's happening inside.

== Start the Application

Use the same command to start a new container with the same name.

[source,bash,role=execute]
----
podman run -d -p 8000:8000 --name hostinfo ${REGISTRY}/hostinfo-app
----

== Execute Commands in a Running Container

One of the most common troubleshooting tools is `podman exec`.
`podman exec` runs a command inside an already-running container. 
The only limitation is whether or not the binary you call is in the image.

For example, you can read the application's current configuration file.

[source,bash,role=execute]
----
podman exec hostinfo cat /app/config.json
----

[source,text]
----
{
  "python_packages": [
    "Flask",
    "gunicorn",
    "distro",
    "pip",
    "non_existent_python_package"
  ],
  "system_packages": [
    "bash",
    "openssl",
    "curl",
    "git",
    "docker",
    "nginx",
    "apache2",
    "non_existent_system_package"
  ]
}
----

The two lists control what the application displays in the UI. This configuration is baked into the image so every new container starts with it.

Dumping file contents with `cat` is fine, but an interactive shell can be a much easier way to troubleshoot.

[source,bash,role=execute]
----
podman exec -it hostinfo /bin/bash
----

The flags `-it` are a common pair when running commands with `exec` against a container to deal with I/O oddities and are key to getting a working shell.

* `-i` interactive STDIN
* `-t` allocate a TTY

You have access to all of the binaries in the image according to the $PATH just like any other environment.
Check what environment variables the container started with:

[source,bash,role=execute]
----
env
----

Now try to list running processes:

[source,bash,role=execute]
----
ps aux
----

[source,text]
----
bash: ps: command not found
----

This is the downside of attempting interactive shell based troubleshooting, `ps` is not in this image. 
The tools need to be shipped inside the image in order for you to use them, pretty straightforward but hard to tell without knowing more about the image.

But there are other ways to get the actual process command being run, like the `cmdline` section of the `/proc` filesystem for PID 1.
Depending on how the container is built, the `CMD` will likely define what is PID 1.
In many cases it's the application itself, but it's also common to see an `init` system of some kind like `systemd`, `runit` or some other process.
Based on how an application behaves when sent a signal, dealing with STDIN/STDOUT/STDERR, child processes, etc, the use of an init system is an architecture choice of the image author.

[source,bash,role=execute]
----
cat /proc/1/cmdline | tr '\0' ' '; echo
----

[source,text]
----
/app/venv/bin/python3 /app/venv/bin/gunicorn --workers 2 --bind 0.0.0.0:8000 app:app
----

Shell troubleshooting can be similar to the experience you'd have on the host, but can also have some strong limits.

[source,bash,role=execute]
----
exit
----

== Process View

Getting inside a container isn't the only way to see what's happening.
There are `podman` tools available that will show you what's going on.

Even though `ps` wasn't included in the image, `podman top` shows the processes inside the container from outside — no `ps` required:

[source,bash,role=execute]
----
podman top hostinfo
----

[source,text]
----
USER        PID   PPID  %CPU  ELAPSED   TTY   TIME  COMMAND
root        1     0     0.00  3m21s     ?     0s    /app/venv/bin/python /app/venv/bin/gunicorn --bind 0.0.0.0:8000 app:app
root        7     1     0.00  3m21s     ?     0s    /app/venv/bin/python /app/venv/bin/gunicorn --bind 0.0.0.0:8000 app:app
----

Notice that the "point of view" of things like user and PID are from inside the container.
This isn't actually running as `root` or `PID 1` on the host, but from the container perspective, there's nothing else in the process table above the `gunicorn` application.

== Resource Usage

You can also get resource views for a container with `podman stats`.

[source,bash,role=execute]
----
podman stats hostinfo --no-stream
----

[source,text]
----
ID            NAME      CPU %   MEM USAGE / LIMIT   MEM %   NET IO        BLOCK IO  PIDS
a1b2c3d4e5f6  hostinfo  0.12%   45.3MB / 3.8GB      1.19%   1.2kB / 890B  0B / 0B   3
----

The `--no-stream` option prints a point-in-time snapshot of CPU, memory, network I/O, and block I/O. 
If you omit that option, it will print continuously.


== Container Configuration

We used `podman inspect` earlier to get the port we needed to map, but there's a lot more information available.
We also mentioned that the `--format` option can be used to specify JSON field directly.

Let's use the format string to inspect the environment variables.

[source,bash,role=execute]
----
podman inspect hostinfo --format '{{.Config.Env}}'
----

[source,text]
----
[PATH=/app/venv/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin container=podman CONTAINER_DEFAULT_USER=65532 PYTHON_VERSION=3.11.16 PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1 HOME=/tmp HOSTNAME=fa0362dd533b]
----

You can see the build time change to the `PATH` to make starting the app easier along with a few other variables.

We can also get the name of the image the container started from.
This can be useful if you are troubleshooting a running container you didn't start yourself.

[source,bash,role=execute]
----
podman inspect hostinfo --format '{{.Config.Image}}'
----

[source,text]
----
registry-xxx.example.com/hostinfo-app:latest
----

[source,bash,role=execute]
----
podman ps
----

The container is still running. None of these tools affected its lifecycle.

We've connected a port to our container and done some inspection of the application inside.
