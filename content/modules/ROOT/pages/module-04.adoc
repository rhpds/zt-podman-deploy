= The Application Host View

So far we've looked at the default container view of the application, but it can also show host details if the right holes are poked in the isolation model for the container.

Open http://hostinfo-{guid}.{domain}[*the hostinfo application*^] and enable the Host View using the toggle.

image::host_view_toggle.png[Host View toggle control]

The warning banner lists the resources the application needs but cannot see.
They exist on the host but have not been made available inside the container. 

image::initial_host_details_errors.png[Host view with warning banner and missing resource indicators]

== Host Hostname

The container view shows the autogenerated container hostname. 
The host view is designed to show the actual host hostname, but the application has no way to discover it across the isolation boundary.
We need to provide it directly, and in the case of this application, we can do that with an environment variable.

[source,bash,role=execute]
----
podman run --replace -d -p 8000:8000 --name hostinfo \
  -v ~/hostinfo-config/config.json:/app/config.json:ro,z \
  -e HOST_HOSTNAME=$(hostname) \
  ${REGISTRY}/hostinfo-app
----

The `-e` option lets us specify environment variables to be passed into the container environment the same way we would for a shell.
Each variable gets a new `-e`, but you can also take advantage of things like environment variable files with `--env-file` if there are many.
Certain types of services like `mysql` or `postgresql` databases might make use of an environment file to pass a number of variables about connection strings, user ids, table names, etc.

Open http://hostinfo-{guid}.{domain}[*the hostinfo application*^] and check the host view. 
The hostname now appears and the error indicator for the missing variable clears.

image::hostname_updated.png[Host view showing hostname populated after HOST_HOSTNAME injection]

== Host Operating System

The next thing to address is the OS distribution is still unknown.

The application reads `/usr/lib/os-release` to display host OS information. 
We can use the same volume mount to pass it read-only like the configuration file.

[source,bash,role=execute]
----
podman run --replace -d -p 8000:8000 --name hostinfo \
  -v ~/hostinfo-config/config.json:/app/config.json:ro,z \
  -e HOST_HOSTNAME=$(hostname) \
  -v /usr/lib/os-release:/host/os-release:ro \
  ${REGISTRY}/hostinfo-app
----

No `:z` here. `os-release` is a host system file — it belongs to the host, not to this container's configuration. 
Relabeling it would attempt to change its SELinux context on the host.
System files being borrowed read-only get `:ro` only.

Reopen http://hostinfo-{guid}.{domain}[*the hostinfo application*^].
The host OS distribution appears and the corresponding warning clears. 
The package table now shows the host context but cannot yet resolve versions without the RPM database.

image::release_info_updated.png[Host view showing RHEL distribution after os-release mount]

image::host_rpmdb_missing.png[Package table showing host context but packages not yet found]

== Host Package Information

The application needs `/var/lib/rpm` to query the host's package database.
Same pattern applies.

[source,bash,role=execute]
----
podman run --replace -d -p 8000:8000 --name hostinfo \
  -v ~/hostinfo-config/config.json:/app/config.json:ro,z \
  -e HOST_HOSTNAME=$(hostname) \
  -v /usr/lib/os-release:/host/os-release:ro \
  -v /var/lib/rpm:/host/var/lib/rpm:ro \
  ${REGISTRY}/hostinfo-app
----

Open http://hostinfo-{guid}.{domain}[*the hostinfo application*^].
Now we have the same visibility to the host details as we did the container details.
Notice that the package list stays the same, since that's controlled via the custom config file.

image::host_rpmdb_updated.png[Package table showing host packages resolved from the RPM database]

The two tabs show two separate views through the same application. 
The container view reflects the image and its baked-in configuration. 
The host view shows only what you chose to make available: the hostname, OS, and packages the container was given explicit access to.

== What's next?

This sample application shows how real services like `httpd` or `mysql` can be run containerized and behave as expected when installed as packages.
Containers are isolated by default from the host, but that can be carefully and strategically changed to connect to networks, access persistent storage, and more.

Here we ran these containers by hand to get familiar with how `podman` behavior changes.
We can run these like typical system services either directly via unit files or as `pods` or `quadlets`.
Check out our other labs to explore those concepts.
