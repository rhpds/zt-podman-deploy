= Configuring the Application

The container's default configuration is baked into the image — the same `config.json` on every run. Configuration that varies by environment or deployment needs to come from outside the isolation boundary. Volume mounts, environment variables, and targeted host path mounts are the mechanisms for doing that deliberately and safely.

== The Starting Point

In the previous module you read the default `config.json` with `podman exec` — two lists that control what the application displays. That file ships with the image and resets every time a new container starts. To change the application's behavior without rebuilding the image, the configuration needs to come from the host.

== Create a Custom Configuration

[source,bash,role=execute]
----
mkdir -p ~/hostinfo-config
----

Create a modified config with a shorter package list:

[source,bash,role=execute]
----
cat > ~/hostinfo-config/config.json << 'EOF'
{
  "python_packages": ["flask", "gunicorn"],
  "system_packages": ["glibc"]
}
EOF
----

== Inject Configuration with a Volume Mount

Remove the existing container and start a new one with the configuration mounted from the host. First, without any SELinux options:

[source,bash,role=execute]
----
podman rm -f hostinfo
----

[source,bash,role=execute]
----
podman run -d -p 8000:8000 --name hostinfo \
  -v ~/hostinfo-config/config.json:/app/config.json:ro \
  ${REGISTRY}/hostinfo-app
----

Check whether the container can read it:

[source,bash,role=execute]
----
podman exec hostinfo cat /app/config.json
----

[source,text]
----
Permission denied
----

The file exists on the host and the path is correct, but SELinux denies the container access. Files in your home directory carry the user's SELinux context — not a context the container runtime is permitted to read.

== SELinux Context

Check the current label on the file:

[source,bash,role=execute]
----
ls -Z ~/hostinfo-config/config.json
----

[source,text]
----
unconfined_u:object_r:user_home_t:s0 /home/rhel/hostinfo-config/config.json
----

The `user_home_t` type is not accessible to container processes. The `:z` volume option relabels the file with a type the container runtime can read:

[source,bash,role=execute]
----
podman rm -f hostinfo
----

[source,bash,role=execute]
----
podman run -d -p 8000:8000 --name hostinfo \
  -v ~/hostinfo-config/config.json:/app/config.json:ro,z \
  ${REGISTRY}/hostinfo-app
----

[source,bash,role=execute]
----
ls -Z ~/hostinfo-config/config.json
----

[source,text]
----
system_u:object_r:container_file_t:s0 /home/rhel/hostinfo-config/config.json
----

The label is now `container_file_t` — a type container processes are permitted to read. Verify the container sees the custom configuration:

[source,bash,role=execute]
----
podman exec hostinfo cat /app/config.json
----

Open http://hostinfo-{guid}.{domain}[*the hostinfo application*^] — the package list reflects what you defined.

* `:z` — relabel for shared access: multiple containers can read this file
* `:Z` — relabel for exclusive access: only this container; do not use on system files shared across the host

== Environment Variables

Some configuration is a value, not a file. Environment variables cross the isolation boundary without requiring filesystem access:

[source,bash,role=execute]
----
podman rm -f hostinfo
----

[source,bash,role=execute]
----
podman run -d -p 8000:8000 --name hostinfo \
  -v ~/hostinfo-config/config.json:/app/config.json:ro,z \
  -e HOST_HOSTNAME=$(hostname) \
  ${REGISTRY}/hostinfo-app
----

Confirm the value arrived inside the container:

[source,bash,role=execute]
----
podman exec hostinfo env | grep HOST
----

[source,text]
----
HOST_HOSTNAME=rhel
----

The host's hostname is now visible to the application as an environment variable. The container received it at startup — no filesystem path required.

== Host Path Mounts

The application's Host View tab is empty by default. It needs access to specific host system paths to show host OS and package information. Mount them read-only:

[source,bash,role=execute]
----
podman rm -f hostinfo
----

[source,bash,role=execute]
----
podman run -d -p 8000:8000 --name hostinfo \
  -v ~/hostinfo-config/config.json:/app/config.json:ro,z \
  -e HOST_HOSTNAME=$(hostname) \
  -v /usr/lib/os-release:/host/os-release:ro,z \
  -v /var/lib/rpm:/host/var/lib/rpm:ro,z \
  ${REGISTRY}/hostinfo-app
----

Each `-v` is a deliberate, targeted exposure: a specific path, read-only, SELinux labeled. The container cannot reach anything else on the host filesystem.

Verify the container sees the host paths:

[source,bash,role=execute]
----
podman exec hostinfo ls /host
----

Open http://hostinfo-{guid}.{domain}[*the hostinfo application*^]. The Host View tab now shows the host OS and package information alongside the container's own view — the same kernel, different OS layers. The container is still isolated from the host, but you've chosen exactly which host resources cross that boundary and how.
