= Configuring the Application

We have a running application, now we can look at ways to modify the configuration.
Remember that `config.json` we looked at earlier?

Open http://hostinfo-{guid}.{domain}[*the hostinfo application*^] and look at the container view.
The application knows it is running in a container, reports the distribution from the image, and shows the autogenerated container hostname. 
The package lists are the defaults we looked at in the container during the last exercise. 
The goal of this module is to replace that configuration in the running container without modifying or rebuilding the source image.

image::container_details.png[Container view showing default OS information and autogenerated hostname]

image::orig_system_pkgs.png[Container view showing default system package list from the image]

Remove the running container.

[source,bash,role=execute]
----
podman rm -f hostinfo
----

`podman rm -f` force-stops and removes the container in one step. 
Use it when you need a clean restart and the running state doesn't need to be preserved gracefully.
You'll see a better approach for iterative changes in a moment.

== Create a Custom Configuration

This application will read a custom configuration file just as it would the one distributed via the image.
This is a fairly common pattern for "service images" like `httpd` or `caddy` where functionality and customizations are easily expressed in config files.

Create a new directory to hold our custom config file.
[source,bash,role=execute]
----
mkdir -p ~/hostinfo-config
----

This application's config is simple JSON, so let's change the packages it'll report on.

[source,bash,role=execute]
----
cat > ~/hostinfo-config/config.json << 'EOF'
{
  "python_packages": ["flask", "gunicorn"],
  "system_packages": ["glibc"]
}
EOF
----

== Inject Configuration with a Volume Mount


How do we get this newly created file into the container if the filesystems are isolated? 
We can bind mount a directory or file to the container with a new option `-v`.
We know the path is `/app/config.json` from our earlier examination of the filesystem.


[source,bash,role=execute]
----
podman run -d -p 8000:8000 --name hostinfo \
  -v ~/hostinfo-config/config.json:/app/config.json:ro \
  ${REGISTRY}/hostinfo-app
----

The arguments for `-v` are the source path, the destination path, and any options we want to pass, separated by colons.
These are very similar to mount options you'd add to `/etc/fstab` to control mountpoints.
Notice that the host path can be relative, starting in the user home directory here.
The destination path must be absolute.
By default, volumes are mounted read-write, so using `ro` allows us to make it read only instead.

Check the logs to confirm the new container started and loaded:

[source,bash,role=execute]
----
podman logs hostinfo
----

[source,text]
----
[2026-11-06 16:08:15,196] ERROR in app: Exception on /data [GET]
....
PermissionError: [Errno 13] Permission denied: '/app/config.json'
----
Well that's pretty ugly python trace, but at the end we see a permissions issue on the new config file.
So the volume is there, but something is wrong.
Let's check via the shell.

[source,bash,role=execute]
----
podman exec hostinfo ls -al /app/config.json
----

[source,text]
----
ls: cannot access '/app/config.json': Permission denied
----

Diagnosing a permission denied error like this normally involves checking permissions along the path, the audit log and more. 
For the purposes of this lab, we'll provide you the right answer.
Eventually `ausearch -m avc -ts recent` would show a SELinux denial. 
In this case, the `user_home_t` label on the file. 
Files in your home directory carry the SELinux label `user_home_t`. 

== SELinux Context

Check the label on the file:

[source,bash,role=execute]
----
ls -Z ~/hostinfo-config/config.json
----

[source,text]
----
unconfined_u:object_r:user_home_t:s0 /home/rhel/hostinfo-config/config.json
----

Container processes are not permitted to read that label by default, so we need a new option.
To fix the labeling issue we can add a new option to the list, `z`.

[source,bash,role=execute]
----
podman run --replace -d -p 8000:8000 --name hostinfo \
  -v ~/hostinfo-config/config.json:/app/config.json:ro,z \
  ${REGISTRY}/hostinfo-app
----
The `:z` volume option tells `podman` to relabel the file to `container_file_t`, a type container processes are permitted to read.

This relabeling is appropriate for `config.json` because it exists solely to support this container — it belongs to the container's configuration. 
The question is not where the file lives but who owns it: files created for the container's use can be relabeled; host system files being borrowed should not be. 
You'll see that distinction applied in the next module.

The other new flag after `run` is the alternative to `rm -f` or `start|stop` cycles.
`--replace` stops and removes the existing container atomically before starting the new one. 
For iterative changes this is cleaner than `rm -f` followed by `run`.
Note that `--replace` creates a new container, so logs start fresh from that point.

== Verify the Change

Check the logs to confirm the SELinux flag fixed the issue.

[source,bash,role=execute]
----
podman logs hostinfo
----

[source,text]
----
[2026-08-17 19:31:04 +0000] [1] [INFO] Starting gunicorn 21.2.0
[2026-08-17 19:31:04 +0000] [1] [INFO] Listening at: http://0.0.0.0:8000 (1)
[2026-08-17 19:31:04 +0000] [1] [INFO] Worker booted
[2026-08-17 19:31:04 +0000] [7] [INFO] Booted worker with pid: 7
----

[source,bash,role=execute]
----
ls -Z ~/hostinfo-config/config.json
----

[source,text]
----
system_u:object_r:container_file_t:s0 /home/rhel/hostinfo-config/config.json
----

The label is now `container_file_t`. The file was relabeled when the volume was mounted with `:z`.

Now check on the application.
Open http://hostinfo-{guid}.{domain}[*the hostinfo application*^]. 
The package list in the container view reflects the custom configuration.
